# 0.1.0 acceptance run

Run on 2026-09-02 against release-0.1.0, macOS, ffmpeg 8.1.2, Go 1.27.0.

This is the batch's whole purpose: the release deliberately left out the cache,
resume, the manifest and both UIs so that real traffic could be measured before
anything was built on top of an assumption. The numbers below are what one
command actually cost, taken from each run's own NDJSON rather than estimated.

## What it was run against

Two Creative Commons torrents from archive.org, not a typical release from a
tracker. They were chosen for a reason that matters more than realism: their
swarms will still be there in a year, so a later version can be compared
against these numbers. A scene release's swarm will not.

## Numbers

Per-file traffic is the delta of the run's cumulative `downloaded` counter
across that file's span, which is only meaningful at `-parallel 1`. Machine
load is recorded because it moved by a factor of six across the session:
**elapsed times are not comparable between runs, traffic is.**

## The defect this run found

On `Sintel_Documentary_by_Ali_Boubred.avi` every one of the 20 capture points
came back with `actual = 0.0s` against requests spanning 175 s to 3331 s: the
same black opening frame written twenty times, reported as twenty successes.
All 20 files were byte-identical by md5, in both the min-traffic and the
min-time run; after the fix the same file yields 20 distinct md5s.

ffprobe states no `pts_time` for H.264 in AVI — only `dts_time` — and the
missing field was parsed as zero. The byte positions were correct, which is why
the run spent real traffic producing nothing. Fixed in TOR-37 (read DTS where
PTS is absent; a keyframe is not reordered, so they are the same value) and
guarded in TOR-38 (a frame landing further from its capture point than the
spacing to the neighbouring one is now `frame_skipped` with code `seek_failed`,
never written to disk). Run D confirms the fix on the live torrent: 20 distinct
frames, one of them legitimately dark.

Two conclusions were wrong before this was understood, and are recorded here
because the numbers alone would repeat them: the AVI's 210.8 MiB looked like a
min-time tuning problem, and "20 frames were produced" looked like criterion 1
being met on that file.

## Against REQUIREMENTS.md section 8

| # | criterion | verdict |
| --- | --- | --- |
| 1 | min-time: 20 frames ≤ 2 min and ≤ 150 MB | **met** where seeking worked — 67.9 and 80.0 MiB, 21–42 s. Not tested at the ~10 GB scale the criterion names: the largest file here is 917 MiB. |
| 2 | min-traffic: the same 20 frames ≤ 60 MB | **met** — 42.1 to 57.1 MiB across every file measured, both before and after the fix. |
| 3 | a repeat run makes no network request | **cannot answer** — the result cache is TOR-18, unbuilt. |
| 4 | cancelling keeps frames; the next run fills the gaps | **half** — cancellation keeps what was produced (exit 3 with results on disk, seen in runs B, C and D); filling the gaps needs resume, TOR-19. |
| 5 | a `private: 1` torrent makes no DHT/PEX request | **cannot answer** — needs a private torrent; both of these are public. |
| 6 | a multi-file torrent yields a frame set per video file | **met for the frames** — every run produced its own set per file. The manifest half is TOR-17, unbuilt. |
| 7 | shifted points are marked in the manifest | **cannot answer** — TOR-17 again. |

Three of seven are answerable by this release by design, and they hold. The
rest wait on the cache, resume and the manifest.

## Caveats worth carrying forward

- The file processing order differed between runs B and C at the same
  `-parallel 1`, so something upstream of the plan is not deterministic. It
  makes two runs harder to line up than they should be.
- There is no way to run a single file of a torrent, which made re-testing one
  AVI cost a run over all six.
- The `-n 20` ceiling runs all stopped on the budget rather than finishing, so
  the last file or two in each is a partial sample.
- Frames were checked for blankness with a mean-luminance threshold picked by
  hand; it flagged genuine dark scenes and end credits as well as the real
  failure. Only the AVI's twenty identical frames were a defect.
